## Дополнительная фича: Подписки на пользователей

Для дополнительной функциональности я выбрал возможность подписываться на других инициаторов, чтобы следить за их актуальными мероприятиями.

### Как устроена база данных
Для хранения подписок добавлена таблица `users_subscriptions`, которая связывает сущность `User` саму с собой (Many-to-Many).
* Таблица хранит `follower_id` (кто подписался), `followed_id` (на кого подписались) и дату подписки.
* Настроен `ON DELETE CASCADE`. Если администратор удалит пользователя, база данных сама почистит все его подписки и отпишет от него других людей.
* Стоит ограничение `UNIQUE` на пару ID, чтобы нельзя было подписаться на одного и того же человека дважды.

### Эндпоинты (Private API)
Фича доступна только авторизованным пользователям.
* `POST /users/{userId}/subscriptions/{followedId}` — подписаться на пользователя.
* `DELETE /users/{userId}/subscriptions/{followedId}` — отписаться.
* `GET /users/{userId}/subscriptions` — посмотреть список тех, на кого я подписан.
* `GET /users/{userId}/followers` — посмотреть своих подписчиков.
* `GET /users/{userId}/feed` — получить ленту событий от моих подписок. Поддерживает пагинацию и сортировку по дате события или просмотрам.

### Особенности реализации
При написании бизнес-логики я постарался учесть основные краевые случаи:
1. Сервер не даст подписаться на самого себя или оформить дубль подписки.
2. В метод `/feed` попадают только те события, которые уже прошли модерацию и имеют статус `PUBLISHED`.
3. Чтобы не нагружать приложение и избежать проблемы N+1, лента новостей собирается одним JPQL-запросом. База данных сама фильтрует авторов через подзапрос `IN (...)`, отсеивает неопубликованные события и делает сортировку под капотом.
